## 第一章：入门 —— Harness 工程

### Agent = Model + Harness

```
Agent = Model + Harness
Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正
Agent ↔ Environment
```

- **Harness 不是「模型之外的一切」**，而是「Agent 边界内、模型之外」的运行与治理层。
- 归属辨析：工具定义、调用适配器、沙箱的**权限与重置机制**属于 Harness；
  沙箱内随行动变化的文件与进程、外部数据库、网页、用户属于 Environment。
- **部署位置不决定概念归属** —— 仿真环境与 Agent 同进程仍属 Environment。
- 直觉：Harness 原指马具，不是限制马的奔跑，而是把力量引到正确方向。

### 五功能职责表（原表摘录）

| 功能 | 职责与核心原则 | 实际例子 | 详见 |
| --- | --- | --- | --- |
| **Context** | 为模型提供感知信息；信息要充分 | 系统提示词、知识库、Agent 状态栏 | 第二、三章 |
| **Tools** | 观察与行动手段；接口要清晰 | MCP 工具、代码解释器、搜索工具 | 第四章 |
| **Constrain** | 设定行为边界；**故障安全默认值，能力默认关闭、必须显式开放** | Claude Code 每个工具默认需授权 | 第四章 |
| **Verify** | 自动判断结果对错；**安全检查只看结构化数据，不看模型自由生成的文本**（后者可能已被提示注入操纵） | Linter、类型系统、结果校验 | 第五、六章 |
| **Correct** | 发现问题自动修正或回退；**在确认无法恢复之前不暴露中间态** | 静默重试、连续失败熔断 | 第二、五章 |

**两类功能重要性不对称**：早期框架关注上下文与工具（让它"能做事"）；
生产级系统的重心已转向约束、验证与纠正（让它"不做错事"）。

### 消融实验（实验 1-1）的结论

各组件**不等价**，衡量标准是**信息能否从别处重建**：

| 组件 | 消融后的后果 |
| --- | --- |
| 工具定义 | 失去行动能力 → 但不会沉默，会**给出格式工整、语气笃定的编造答案** |
| 工具执行结果 | 闭环断裂 → 盲目执行，反复重试直到耗尽迭代预算 |
| 思考过程（reasoning） | 当前者可从工具结果重建时，丢掉**几乎没有代价** |
| 历史消息 | 允许冗余操作、重复犯错 |

> 核心洞察：**上下文决定了 Agent 能看到什么，而 Agent 只能基于它看到的信息做决策。**
> 更重要的一条：**"给出了回答"不等于"完成了任务"** —— 上下文残缺时的典型失败不是报错退出，
> 而是一个看上去毫无破绽的答案。

### 五个贯穿全书的设计模式

1. **提议者—审核者**：产出与评判由**不共享上下文**的角色分别承担，评判方只看产物
   （渲染结果、测试输出、结构化参数），**不看产出方的推理过程**。前提是**自审不可靠**。
2. **渐进式披露**：先给可检索的目录，再按需加载细节。同时优化上下文预算与选择精度。
3. **只增不改（Append-only）**：状态以追加演进，已写下的不再回头改。
   换来**可缓存、可重放、可审计**。
4. **边界集 + 保留集**：任何修改都要同时在"应当改变的那批"与"不应当影响的那批"上验证。
   只测前者会把过拟合当进步，只测后者会把无效修改当安全。
5. **最小 diff + 可回滚**：每次修改尽量小、带来源、可单独回滚 —— **让归因成为可能**。

## 第二章：上下文工程

### 上下文的构成

**API 视角**：四种消息角色（`system`/`user`/`assistant`/`tool`）+ 顶层 `tools` 字段
= 五个组成部分。

**结构视角**：`上下文 = 静态前缀 + 轨迹`
- 静态前缀 = 系统提示词 + 工具定义（保持不变）
- 轨迹 = 用户消息 + 模型回复 + 工具执行结果（不断增长）

**关键结论**：**Harness 的核心工作就是管理这个 messages 列表** ——
在合适时机追加消息，然后把整个列表送给模型。后续所有上下文技术本质都是在优化这个列表。

### KV Cache 三条铁律（书里明确标注为"只需记住这三条"）

1. **系统提示词和工具定义一旦确定就不要改。** 任何改动，哪怕多一个空格，都可能改变
   token 序列，使首个不同 token 及其后的缓存无法复用；**改动越靠前，延迟和成本影响越大**。
2. **动态信息永远追加到末尾** —— 时间戳、用户状态等，作为新消息追加到对话末尾，
   而不是修改已有的系统提示词。
3. **使用标准 API 格式，不要自行拼接消息**。自行拼成 `"USER: ... ASSISTANT: ..."`
   的根本问题是**偏离了模型训练时见过的格式**，会削弱多步思考能力。

### 五种错误上下文管理模式（实验 2-3）

| 模式 | 为什么有害 |
| --- | --- |
| **动态系统提示词** | 缓存全废（经典案例：注入 `Current time: {{now}}`，首 token 延迟 0.5s → 3-5s，账单翻倍） |
| **动态用户配置** | 同上 |
| **工具定义动态排序** | 工具定义占篇幅大，改顺序使缓存从首个变动的工具起失效。实测**保持固定顺序对模型选工具能力几乎无影响** |
| **滑动窗口裁历史** | ①破坏前缀一致性；②**丢失关键工具结果** → Agent 陷入循环反复调同一工具 |
| **文本格式化消息** | 最具破坏性。模型需额外注意力推断角色边界 → 重复执行、忽略工具结果、该调工具却生成文本 |

### 缓存作为架构约束（Claude Code 的实践）

- **提示词结构由缓存边界决定**，其次才是语义逻辑。每个运行时条件（OS、模式、语言）
  若放在缓存边界之前，会把缓存键变体翻倍 —— **N 个二值条件产生 2^N 种缓存键**。
  所以**所有动态元素都要放到边界之后**。
- **子 Agent 必须与父 Agent 字节级对齐**（提示词、工具定义、模型配置、消息前缀、思考配置）
  才能命中缓存。
- **工具结果的替换字符串在首次出现时就被冻结**，会话重启后用完全相同的串。
- **改前缀不只是多花钱，还可能丢掉推理**：Anthropic 的 preserved thinking 用签名把
  thinking block 绑定到产生它时的前缀上；前缀一改，该 block 及其后所有 thinking 都失效。
  新账户默认直接 400。

> 官方原话：**让 thinking 失效的改动，正是让缓存从头计算的那些改动。**
> 易踩的写法：每轮重建系统提示词、每轮重渲染首条用户消息的环境信息、
> 中途增删 `tools`、原地截短旧工具结果、往旧消息插提醒又删掉。
> 解法统一为：**把变化追加到末尾**。

> **核心启示：缓存经济性不是事后优化，而是前置约束。**

### Agent 状态栏（Context 侧的动态注入）

像手机顶栏显示时间/电量/信号一样，在**上下文末尾**注入动态元信息
（任务进度、环境观察摘要、工具调用计数），弥补模型无法主动归纳隐式状态的不足。

**注意**：必须在**末尾追加**，绝不能放进静态系统提示词（那会破坏缓存）。

## 第四章：工具

### ACI（Agent-Computer Interface）

工具应对应 Agent 的**目标**，而不是底层的 API 操作。对标 HCI 提出。

### 专用工具 vs 通用执行器 vs Skill

**默认取向：通用工具优于专用工具，除非有明确的安全、权限或性能理由。**
理由：**LLM 本身有强大代码生成能力，应利用它而不是限制它** ——
一个 `code_interpreter` 可代替数十个特定工具，还能处理没想到的边缘场景。

**四种情况该退回专用工具**：
1. **安全/权限/审计**（生产库写操作）
2. **屏蔽平台差异、给出更好反馈**（grep/find 在 Mac/Win/Linux 语法不同）
3. **使用频率极高**
4. **参数结构复杂**（嵌套对象、多字段联合校验）

**参数复杂度为何重要**：原生工具用 JSON schema，推理引擎甚至用限制采样强制格式；
Skill 是自然语言，模型需自己处理引号转义，**且各平台不同** →
**参数复杂时 Skill 更易出错**。折中：让 Agent 把结构化参数写文件再导入。

### 工具描述的三条硬纪律

1. **说清「什么时候用」，而不只是「能做什么」**。
   反例：「搜索相关内容」；正例：「当需要获取实时信息或查找未知事实时使用」。
2. **明确边界（做不到什么）** —— 书原话：
   *大多数工具调用失败的根因不是模型不知道工具能做什么，而是不知道工具不能做什么。*
3. **参数用具体例子代替抽象规范**。
   反例：「`phone`：使用 E.164 格式」；
   正例：「`phone`：电话号码，E.164 格式（国家代码+号码，无空格），例如 `+8613888888888`」。

**返回值也要描述**，耗时长的工具**注明执行代价**（帮助模型规划调用顺序）。

**附 1-5 个真实调用示例**：JSON Schema 只能描述类型，无法表达调用方式与典型参数组合；
加示例后准确率可从约 72% → 90%。

> **调试原则**：当 Agent 频繁选错工具时，**优先检查工具描述**而不是怀疑模型能力。
> 修正描述的投入产出比远高于换更强的模型。

### 参数传递的保真性（硬约束）

两种反模式：
- **静默输入转换**：Cursor 曾把中文弯引号静默转成直引号 → 模型读取工具看到弯引号、
> 原样传入替换工具，但参数层已转换 → 反复"未找到匹配"，
> **模型无法理解为什么工具找不到自己明明看到的内容**。
- **静默参数注入**：某 IDE 的 bash 工具在 `git commit` 时自动追加参数 → 旧版 git 报错，
> 模型反复改措辞都失败。

> **原则：模型感知到的世界与工具操作的世界之间，不能存在系统性的偏差。**
> 确需规范化时，**必须在工具描述中说明，并在返回中明确告知模型**。

### 工具太多：三层解法

工具数超一百个时，即使最强模型也容易选错。
1. **层次化组织与按需加载**（只暴露索引；Cursor A/B 测试 token 消耗降 46.9%）
2. **主动工具发现**（MCP-Zero：约 2800 个工具上比全量注入省 ~98% token）
3. **Skills**（目录项只占几十 token，正文用到才读）

### 第三方能力风险

- **工具描述投毒**：description 会原样进模型上下文，可夹带指令。本质是提示注入的变种，
  **注入载体从用户输入换成了工具定义本身**。
- **同名工具遮蔽**：恶意服务器遮蔽正规工具，诱导把敏感参数路由到攻击者。

## 第五章：Coding Agent 与通用 Agent

### 为什么 Coding Agent 成熟度最高

任务清晰度 × 验证自动化程度四象限：

| | 结果可自动验证 | 结果需人工验证 |
| --- | --- | --- |
| **目标明确** | **最佳区域**：修有测试的 bug | 吞吐受限：重构需人审 |
| **目标模糊** | 高效地跑偏 | 难以启动 |

> 不是因为代码生成模型特别强，而是因为**软件工程几十年积累的基础设施
> 天然构成了一套强大的 Harness**：测试套件提供验收标准，Linter/类型检查器提供即时验证，
> Git 提供完美的版本控制与回退。

### Harness 在 Coding Agent 的四个组件

- **验收基线**：什么算做完了 —— 测试套件、CI、审查标准
- **执行边界**：能碰什么 —— 模块边界、依赖规则、权限控制
- **反馈信号**：自动对错判断 —— Linter 输出、测试结果、类型错误
- **回退手段**：出了问题怎么恢复 —— Git、沙盒隔离、快照回滚

### 四条可迁移设计原则

1. **约束优先于指导**：能用代码强制的就不要用文档建议。
   Linter 规则的价值远超系统提示词里「请遵循…」—— **前者是"做不了"，后者只是"建议别做"**。
2. **验证要自动化**：人工审查是不可扩展的瓶颈。
3. **反馈越快越好，越结构化越好**：错误信息越详细、越接近错误发生时刻，纠正效率越高。
4. **回退要可靠**：Agent 在安全网内才能大胆试错。

### 过程约束（不只是结果）

> 修复数据库故障时直接把库删了重建，"修复"确实生效，但数据没了。
> 即使把限制写进最终评估指标，Agent 也常能找到绕过去的办法（reward hacking 的日常形态）。
> **因此要对 `rm -rf`、删除生产数据、覆盖未读文件这类危险动作设置专门的检查与审批 ——
> 约束的是动作，而非仅仅是结果。**

### 故障分类学（四层）

- **API 层**：限流 429、服务过载、超时、连接中断、输出触顶被截断
- **工具层**：幻觉调用（工具不存在）、参数畸形、执行抛异常、
  **最危险的一种 —— 工具反复返回同一个错误，而模型不加改变地反复重试**
- **上下文层**：窗口溢出、压缩失败、轨迹结构损坏（工具调用缺少配对的结果消息）
- **控制流层**：死循环（反复执行相同操作却毫无进展）、**死亡螺旋**（恢复逻辑自身又调 LLM、再出错、连锁）

### 检测：先分类，再计数

第一个判断不是"要不要重试"，而是**"值不值得重试"**：
- **可重试**：限流、过载、网络抖动
- **不可重试**：参数不合法、权限不足、工具不存在 —— **原样重试多少次都是同样结果**

**模式检测**：
- **重复调用指纹**：对「工具名 + 参数」计算指纹，相同指纹反复出现 = 无进展循环的明确信号
- **连续失败计数**：每条恢复路径维护独立计数器，为熔断提供依据

**活性监控**：流式连接最危险的失败不是断开（会立即报错），而是**静默卡死** ——
连接建立成功但数据流停止。SDK 超时往往只覆盖初始连接而非传输过程 →
需要独立的**空闲看门狗**。可推广为：**每个长连接都需要活性信号，而非仅依赖连接超时**。

**完整性监控**：发现工具调用缺少配对结果时，**在注入上下文前自动修复配对**，
而不是把结构异常抛给模型或用户。
> 工程细节：部分生产 Agent 同时跑"产品模式"与"训练数据收集模式" ——
> 产品模式用占位符修补缺失消息，**训练模式拒绝修复**（合成占位符会污染训练数据）。

### 恢复：分级升级，逐级透明

1. **静默重试**：指数退避 + 随机抖动（避免同步重试造成二次拥塞）、尊重服务端等待提示、
   **区分前台与后台调用**（后台失败直接放弃，否则"重试放大"挤占主链路配额）
2. **降级与接续**：输出触顶 → 先提升上限重发，再追加元指令从断点续写；
   主模型过载 → 降级备用模型（**需先剥离旧模型私有格式块**）
3. **暴露给用户**：所有自动手段用尽后才呈现，**并附上已尝试的恢复动作**

**工具层错误走另一条路**：**不终止会话，把错误变成模型的输入**。
幻觉调用收到"工具不存在"的结构化错误；参数校验失败收到附带约束提示的错误；
畸形参数在执行前先经程序化修复。**这些错误以普通工具结果的身份进入上下文，
由模型在下一轮自行纠正。**

> **核心原则：错误处理的边界不是单次请求，而是整个恢复循环。**
> 在确认无法恢复之前，中间错误不应暴露给消费者 —— 无论是用户还是下游订阅系统。

### 接管：把没跑完的轨迹交给另一家模型

> **跨厂商接管能带走的是文字，带不走的是凭证。**
> 思考通常两部分：可读的文字 + 厂商附的凭证（证明这段思考出自它自己）。
> 文字换一家仍读得懂，凭证换一家就失效。

设计原则：
- **轨迹保存为中立格式**，不按任何一家的接口格式存储。
- 每段思考拆成**可移植的文字**与**不可移植的凭证**。
- 工具调用只记录**名称与参数**，标识符在渲染成具体请求时**按目标厂商重新生成**。
- 切换时凭证一律丢弃，文字以普通内容身份带入，**不塞回目标厂商放思考的位置**。
- 方案要**按最严格的一端设计**，并为满足不了的情形准备退路
  （把历史工具调用改写成文字叙述）。

中立格式的额外价值：**第七章的评估重放、第八章的训练样本构造、
第九章的经验提取，依赖的都是同一份产物。**

### 五个实现技巧

1. **并行工具调用、流式执行与级联中止** —— 第一个工具调用参数一完整通过校验即可开始执行，
   与后续调用的生成重叠；独立调用可并行。
   故障时**级联中止同一批并行且依赖该结果的其他调用，但不波及独立调用与父级操作**。
2. **上下文精细化管理** ——
   - 文件读取：支持按行号范围读片段；**返回内容时附加行号标注，每行以实际行号作前缀**。
     价值：模型可精确引用「第 42 行」，减少歧义，使后续编辑更可靠。
   - 命令输出：保留前若干行（错误上下文）与后若干行（错误总结），中间以一行提示替代，
     并**说明完整输出已保存到临时文件供按需查看**。
3. **环境信息动态注入**（Agent 状态栏在 Coding 场景的体现）：当前工作目录、git 分支、
   最近提交、未暂存/已暂存的变更概览。**不应硬编码进静态系统提示词**（破坏缓存），
   而应作为**追加式**状态栏实时生成。
4. **命令执行环境状态持久化** —— 维护**持久化终端会话**，保留工作目录、环境变量、会话状态
   （`cd` 之后下一条命令不该回到根目录；`source venv` 的效果只在当前 shell 有效）。
   也应保留启动隔离终端的能力以支持并行任务，但**持久化会话应是默认模式**。
5. **即时语法反馈** —— 文件写入一完成，工具层**自动运行 linter/语法检查**，
   把结果作为**工具返回值的一部分**。像 IDE 打错括号立刻画红线一样。

### 搜索工具的四种方式

| 方式 | 能力 | 局限 |
| --- | --- | --- |
| **正则内容匹配**（grep/rg） | 知道具体文本时快速准确定位；支持类型/路径过滤 | **只能字面匹配，不懂语义** |
| **文件名模式**（glob） | 不看内容只看路径，快得多；探索项目结构的第一步 | 同上 |
| **语义代码搜索** | 理解"意义"，找语义相似但用词不同的代码 | 需维护索引；**业界有路线之争** |
| **符号级定义/引用查询** | 区分定义与调用 | 主流 coding agent 尚未采用 |

> 路线之争：**Claude Code 刻意不建嵌入索引，纯靠 agentic 的 grep + glob 现场检索** ——
> 不必维护随代码演化而陈旧的索引，也省掉一整套索引基础设施。
> Cursor 早期走相反路线（建索引换跨文件语义召回），**目前也改用 grep + glob 现场检索**。

### 五种文件编辑方案

| 方案 | 代表 | 特点 |
| --- | --- | --- |
| 差异描述 + Apply Model | Cursor（早期） | 职责分离；**合并环节脆弱**（相似片段可能合并错位置）。已不再使用 |
| **旧字符串 → 新字符串** | **Claude Code、Codex、今天 Cursor** | 可预测、透明；存在且唯一则成功，否则失败，**无模棱两可**。代价：删大段需完整输出原文 |
| 行号定位 | — | 精确无歧义，大段删除只需两个数字。问题：**每次编辑后行号都会变** |
| 类 Vim 命令 | — | 重组代码高效；**对模型不友好**（模型难以预计算修改后的行号） |
| 字符串首尾匹配 | — | 折中：兼顾可靠性与效率，中间可省略 |

> 深刻的一点：**Vim 等编辑器是为人类设计的 —— 人类需要不断看到当前状态并规划下一步的简单操作；
> 而模型的工作模式是经过较长时间的思考，再批量进行较为复杂的操作。**

### 安全：致命三要素

Simon Willison 的「致命三要素」：
1. **访问私有数据** 2. **暴露于不受信任内容** 3. **具备外部通信能力**
→ 攻击路径闭合：恶意指令藏在不信任内容中进入 → 驱使它读私有数据 → 经对外通道传出。

**书补充第四个维度：持久记忆** —— 不是并列的必要条件，而是**攻击的放大器**：
把偏见/恶意指令写入长期记忆，**跨会话潜伏**，把一次性攻击升级为长期威胁。

四类边界：数据边界、输入信任边界、输出影响边界、跨会话边界。

> 面对提示注入，**单靠输入过滤基本挡不住**。重点不是识别所有攻击，
> 而是**让 Agent 即使被注入，也没有机会把危险动作真正执行出去**。

## 我对本书的关键取舍

1. **上下文纪律是全书的硬约束**，也是最容易做错、错了代价最大的一块。
   本项目把「前缀不变」做成**可断言的测试**（`prefix_hash()`），而不是口头纪律。
2. **中立轨迹格式**是第五章最有价值的工程结论，且被第七、八、九章复用 ——
   我们一开始就按中立格式设计，不做厂商绑定。
3. **验证只看结构化数据**（§1）—— 这条决定了 `verify.py` 的接口：
   它**不能**接收模型的自由文本作为判据。
4. **约束优于指导**（§5）—— 能用代码强制就不用文档建议。
   这决定了 `policy.py` 是**判定函数**而不是提示词段落。
