# Codex 架构原理调研（2026-10 版）

> 本文是本项目「对标 Codex 的综合 agent」的架构参考基线。
> 信息源：OpenAI 官方工程博客、Agent Patterns Catalog、VS Code 官方文档、
> 以及多份 2026 年的工程实践分析。凡标注「推断」的条目，是社区观察而非官方披露。

---

## 一、产品矩阵：一个内核，三个入口

Codex 不是一个 IDE，也不只是一个 CLI。它是**同一个 agent 内核 + 三种外壳**：

| 入口 | 形态 | 定位 |
| --- | --- | --- |
| **Codex CLI** | Rust 单文件二进制，终端 TUI | 终端原生、可脚本化（headless） |
| **IDE 扩展** | VS Code / Cursor / Windsurf / JetBrains 插件 | 编辑器内受监督会话 |
| **Codex Cloud** | `chatgpt.com/codex` + 云端沙箱 | 后台任务、并行委派 |

**关键工程决策：三端共用一套配置**（`~/.codex/config.toml`、`AGENTS.md`、MCP 配置）。
CLI 里配好的沙箱策略与 MCP server，IDE 扩展直接复用。这是「一次配置、两端通用」。

**核心形态选择**：IDE 扩展**不做行内 ghost-text 补全**（那是 Copilot 的活）。
Codex 走的是**侧边栏 agent 面板**路线——它不是自动补全层，是一个跑在编辑器里的 agent。
这个取舍非常重要：意味着我们的前端是「agent 工作台」，而不是「编辑器 + AI 提示」。

## 二、总体架构：四层

```
┌─────────────────────────────────────────────────────────┐
│ 入口层   CLI TUI ｜ IDE 扩展 ｜ Cloud                     │
├─────────────────────────────────────────────────────────┤
│ 协调层（Harness / agent runtime）  ← Rust 编写            │
│   · Agent Loop 调度   · 工具编排   · 沙箱与审批判定        │
│   · 上下文装配与压缩   · 提示词缓存维护                    │
├─────────────────────────────────────────────────────────┤
│ 上下文层                                                 │
│   · AGENTS.md 指令链（分层）   · .codexignore             │
│   · 会话历史（append-only）    · 代码库索引                │
├─────────────────────────────────────────────────────────┤
│ 工具层                                                   │
│   apply_patch ｜ shell ｜ rg 代码搜索 ｜ 测试 ｜ MCP        │
└─────────────────────────────────────────────────────────┘
```

官方把协调层明确称为 **agentic task execution framework（代理任务执行框架）**，
并强调它是 **Rust 编写**、连接模型/工具/用户环境的中间层。
**这一层的性能优化才是 Codex 的真正护城河，不是模型本身。**

## 三、Agent Loop（ReAct 风格）

Codex 的主循环是教科书式的 ReAct 工具使用循环：

```
用户目标（自然语言）
      │
      ▼
┌─→ 上下文装配（目标 + 仓库状态 + 历史轮次 + 工具结果历史）
│         │
│         ▼
│   模型推理 ──→ 产出：自然语言（给用户）｜ 结构化工具调用
│         │
│         ▼
│   沙箱策略 × 审批策略 → 判定：执行 / 询问 / 拒绝
│         │
│         ▼
│   工具执行 → 捕获 stdout / stderr / exit code / diff
│         │
│         ▼
└── 结果回填上下文，循环继续
      │
      ▼
终止条件：模型声明完成 ｜ 撞上审批门 ｜ 预算耗尽
```

### 事件流协议（前端必须实现的部分）

循环中每个事件都带**精确的类型标记**，客户端据此做流式 UI 更新：

- `reasoning` —— 推理过程增量
- `tool_call` —— 工具调用请求
- `tool_result` —— 工具执行结果
- `response_complete` —— 本轮结束

> **对本项目的要求**：前端不能只画一个「转圈 + 最后出结果」。
> 必须逐事件流式渲染：推理文本、工具调用卡片、结果回填，全部实时。

## 四、上下文工程：Codex 最值钱的部分

### 4.1 AGENTS.md 指令链

启动时读取，**分层**（仓库根 → 子目录逐级叠加），形成指令链。
用途：把「构建/测试命令 + 不要动的目录 + 项目约定」写进几百 token，
替代 agent 自行探索项目结构所消耗的几万 token。

OpenAI 内部案例：88 个 AGENTS.md 文件，7 人 5 个月完成 100 万行代码、合并 1500 个 PR。
**上下文管理是工程纪律，不是靠更大的窗口。**

### 4.2 七层 Prompt 设计 + 提示词缓存

Codex 的 prompt 分七层，**前面若干层是静态或半静态的**，可以精确缓存。
缓存命中时，模型采样成本从二次复杂度降为**线性**——
即使对话进行几十轮、累计数千万 token，每轮边际成本仍可控。

**为保住缓存前缀，harness 强制三条纪律：**

1. **模型可见的记录一律 append-only**：新消息、工具结果、环境更新只追加在末尾，
   **绝不插入较早的上下文**（插入 = 前缀失效 = 缓存全部击穿）。
2. **工具按固定顺序呈现**。
3. **运行时设置（如审批策略）运行时套用，不嵌进工具定义**。
   （因为审批策略中途可能被用户改，一旦嵌进工具定义，前缀就变了。）

> 这是最容易被抄漏、也最致命的一条。
> 很多自研 agent 为了「让上下文更整洁」而做历史重排/压缩插入，直接毁掉缓存命中率。

### 4.3 自动上下文压缩：加密的「肌肉记忆」

当对话 token 超过阈值，自动调用 `/responses/compact` 端点。
**注意：它返回的不是文本摘要，而是一个不透明的加密 blob**，
编码了模型对整段对话的 latent understanding（潜在理解）。

三个优势：
- **保真度更高**——文本摘要必然丢细节，latent state 保留了深层理解
- **支持零数据保留（ZDR）**——密钥在服务端，原始数据不留存
- **对用户透明**——后台自动，无需干预

代价：人类读不了这个 blob，也无法选择保留/丢弃哪部分信息，**存在供应商锁定**。

> **对本项目的启示**：我们自研时拿不到 `/responses/compact`。
> 现实做法是**分层摘要 + 结构化工作记忆**（计划状态、已改文件、未解问题单独留），
> 而非一股脑文本摘要。压缩策略要设计成可读、可控。

### 4.4 代码库索引 + 惰性探索

流程：**构建索引 → 查询索引确定相关文件 → 只把相关文件载入上下文**。
多阶段方法，避免把整个代码库塞进窗口。

**延迟探索（lazy exploration）**：集成功能、自定义 MCP 工具、技能、插件
**只在模型需要时才向它呈现**，防止一大堆工具定义把上下文窗口占满。

**工具输出硬上限：默认 10,000 token**（除非模型显式要求更高）。
这是纯工程理性的设计——一次 `find` 或一坨测试日志就能吃掉半个窗口。

## 五、沙箱 × 审批：正交的双轴模型

这是 Codex 安全设计的核心。**两把旋钮是独立的**：

### 沙箱模式（决定「能碰什么」）

| 模式 | 文件系统 | 网络 |
| --- | --- | --- |
| `read-only` | 只读，可检查可提议 | 只读访问通常受限 |
| `workspace-write` | 可在项目工作区内写 | 默认受限 |
| `danger-full-access` | 无沙箱 | 全开，**无审批** |

### 审批策略（决定「什么时候问你」）

| 策略 | 行为 |
| --- | --- |
| `untrusted` | 每条有后果的 shell 命令都要批准 |
| `on-request` | 沙箱内自动放行，越界才问（**默认推荐**） |
| `never` | 全自动，不打断 |

默认值应写在 `~/.codex/config.toml`，**而不是靠人记 flag**。
（原话大意：在时间压力下没人记得住 flag，配置默认值才是可靠的安全带。）

**判定原则（社区提炼的教学口径）**：
> 如果一次运行的最坏结果是「一个烂 diff」→ 放它写。
> 如果最坏结果涉及网络或包管理器 → 必须有人在审批路径上。

`/permissions` 可在会话中途切换审批策略。

## 六、工具层

| 工具 | 作用 | 设计要点 |
| --- | --- | --- |
| **apply_patch** | 结构化 diff 补丁，create/update/delete 文件 | 核心编辑原语，非「整文件重写」 |
| **shell** | 命令、脚本、构建、测试 | 受沙箱约束 |
| **rg (ripgrep)** | 代码搜索定位 | **优先用专用工具而非裸 shell** |
| 测试与验证 | 自动探测测试框架，跑最小相关集 | 不跑全量 |
| **MCP** | 外部工具扩展 | CLI 与 IDE 共享同一份配置 |

所有执行结果（stdout / stderr / diff / 测试结果）**都经过标准化处理**再回填。

**编辑纪律**：先读取足够上下文，再**批量执行逻辑编辑**，避免反复微量编辑。
（微编辑 = 多轮往返 = 重复上下文传输 = 成本爆炸）
所有编辑遵循现有代码库约定：命名风格、格式化、本地化。

**搜索纪律**：用 rg 搜代码、**并行读取多个文件**，
优先专用工具、**最大化并行化工具调用**。

## 七、多 Agent 与并行

- **模型分层**：主代理用旗舰模型（GPT-5.x）做推理，
  子代理用轻量模型（GPT-5.x-mini）执行**快速并行的子任务**。
  简单任务不烧旗舰额度。
- **并行探索**：可委派多个 subagent 同时探索不同方案路径，然后汇总结果。
- **Subagent + Worktree**：每个子代理独立 worktree、独立上下文，互不污染。
  这是大型重构中途不失一致性的关键（单线程上下文覆盖不了全局）。
- **渐进式检查**：Builder 每次只计划一部分，做完让 Reviewer 轻量检查，
  再动态调整后续计划——而不是「一次性制定完美计划然后 rigid 执行」。

## 八、`/goal`：Ralph Loop 的原生实现

双模型架构：

- **Worker 模型**：负责实际工作（读写文件、跑命令、实现功能）
- **Evaluator 模型**（轻量，如 Haiku 档）：**每回合结束独立检查目标条件是否满足**

Evaluator **只关心「证据是否充分」，不参与实际工作**，所以判断更客观。
且它成本比 Worker 低约 10–20 倍，使「频繁检查」在经济上可行。

> 这是「自证（self-verification）」落到架构层的实现方式，
> 也是我们前端要展示的重要一环：**当前回合是否满足目标、证据是什么。**

## 九、IDE 扩展的前端形态（我们要对标的 UI）

### 布局

- **侧边栏面板**为主（VS Code 默认在右，可拖到左）。
  主流分工是「代码在左、agent 在右」。
- **Agents window**（VS Code 原生 Preview，2026）：
  - Sessions list —— 跨 workspace 的会话列表，按 workspace 分组
  - Chat area —— 对话与输入
  - Changes panel —— 本次会话的改动
  - Files panel —— workspace 文件浏览
  - Terminal and Tasks —— 会话所属 worktree 里跑的终端与任务
  - Browser —— 会话所属的浏览器标签与页面状态
  - Customizations panel —— 自定义（automations 等）

### 对话模式（三档，映射到沙箱）

| 模式 | 行为 |
| --- | --- |
| **Chat** | 可读文件、回答问题；编辑/命令/联网都要批准（≈ CLI 的 read-only） |
| **Agent**（默认） | 读文件、工作区内编辑、跑命令；越界（网络/项目外）才要批准 |
| **Agent (full access)** | 同上但网络全开、无审批提示 |

### 交互细节

- **输入框左侧 `+` 上下文菜单**：Add file context / Add image context。
  文件要**手动检索文件名**（不像文件树那样自动列举）。
- **Auto context** 开关：自动把当前打开的文件纳入上下文。
- **`@file` 引用**：在 prompt 里直接标注文件，模型不必猜。
- 编辑器内**选中代码右键 → Ask Codex / Codex Edit**
  （前者只问不改，后者直接改选中部分）。
- **Task history**：按时间倒序的会话历史，可进入任意一段继续。
- **Settings** 分四块：Codex Settings / IDE Settings / MCP Settings / 快捷键。
- 执行中实时显示：**执行步骤流 + 读过的文件 + 当前状态**（「正在跑测试」「正在编辑文件」）。
- 结果审查两块核心信息：**文件变更清单**（含变更类型）与**测试运行结果**，
  点任一文件看详细 diff。

### 已明确的产品边界

- 不做行内补全。
- 异步任务启动后**无法立即终止**（社区反馈的痛点）——
  > **本项目可以做差异化**：把「可中断」做成显式能力。

## 十、Codex 明确做不好的事（我们自己要规避或显式暴露）

1. **内部库最近改过签名** → 它会自信地调用旧签名。
2. **需要看到运行中的系统才能调试** → 看不见就只能猜。
3. **大规模重命名遇上动态分发 / 字符串查表** → 它抓得到静态调用点，漏掉反射的。
4. **判断「这个改动是不是个好主意」** → 它会非常能干地实现一个烂计划。
5. **长时间无人值守处理模糊任务** → 模糊不会随时间收敛，只会累积。

**能显著改善结果的三件事（都不是 prompt 技巧）**：
1. 仓库根放一份简短 `AGENTS.md`：构建/测试命令 + 不该动的目录。
2. **测试输出在成功时保持安静**（`pytest -q`）——给 agent 干净信号，而不是一堵警告墙。
3. 给它**自检手段**，让它「检查通过就停」，而不是「想不出办法才停」。

## 十一、本项目（code-agent）的复刻清单

| 层 | Codex | 本项目计划 |
| --- | --- | --- |
| 外壳 | CLI + IDE + Cloud | 先做 **Web 版 IDE 工作台**（单页静态，可直接双击打开） |
| 协调层 | Rust harness | 后端 Python 标准库（参考既有 harness 方案，零依赖） |
| 上下文 | AGENTS.md + 七层 prompt + 缓存 | AGENTS.md 等价物 + **append-only 历史**（保住前缀） |
| 压缩 | `/responses/compact` 加密 blob | 分层摘要 + 结构化工作记忆（可读可控） |
| 沙箱 | 三档 × 三档正交 | 前端先把**模式选择器 + 审批门 UI** 做出来 |
| 工具 | apply_patch / shell / rg / MCP | apply_patch 语义的 diff 卡片 + 工具调用卡片 |
| 多 agent | subagent + worktree | 会话/任务多轨视图（前端先出结构） |
| 前端 | 侧栏面板、事件流、diff、审批 | **本次交付目标** |

**差异化机会**（Codex 的已知短板，我们做亮点）：
- **显式可中断**：每个运行中的工具调用 / 任务都能一键中止。
- **压缩可见**：让用户能看到「压缩了什么、留下了什么」。
- **证据链**：每个结论旁边挂上它依据的工具结果（可点开溯源）。

## 附录：关键配置与命名

```toml
# ~/.codex/config.toml（示意）
sandbox_mode = "workspace-write"        # read-only | workspace-write | danger-full-access
approval_policy = "on-request"          # untrusted | on-request | never
preferred_auth_method = "chatgpt"       # 或 "apikey"
```

斜杠命令：`/plan`（先出计划）、`/resume`（续接会话）、
`/permissions`（切审批策略）、`/mcp`（管 MCP）、`/status`（看 token 消耗）、`/goal`（Ralph Loop）。

`apply_patch` 是**结构化 diff 工具**，不是文本替换——
它按「新增/更新/删除文件」语义操作，这样才可审计、可回滚。
