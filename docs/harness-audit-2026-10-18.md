# Harness 审计报告（2026-10-18）

审计对象：`harness/` 全部 29 个生产模块、约 13,100 行（不含测试）。
方法：**机械扫描 + 逐项定性**，不凭印象。七类检查各自有可复现的判据脚本。

结论：**发现 11 个真实缺陷，全部修复**。其中 **5 个**属于"看起来正确、实际从不生效"，
比"功能缺失"危险得多 —— 前者会让读代码的人以为防线存在。

---

## 一、审计判据（每类怎么查的）

| # | 类别 | 判据 | 结果 |
|---|---|---|---|
| 1 | 死代码 / 空壳 | AST 提取所有公共定义，统计生产代码里的引用次数 | 32 个未被引用，**4 个是真空壳** |
| 2 | 配置项失效 | `LoopConfig` 每个字段是否被 `cfg.<field>` 读取 | 16/16 全生效 |
| 3 | 静默吞异常 | AST 找 `except` 体为 `pass`/`continue`/`return <const>` | 38 处，**1 处需留痕** |
| 4 | 判据重复 | 同名表在几个模块各定义一份 | **5 份副本，已漂移** |
| 5 | 协议自检 | `assert_*` 是否有调用点 | 3 个自检，**1 个无调用点 + 恒真** |
| 6 | 资源泄漏 | 句柄/子进程回收路径 + 未用 `with` 的 `open()` | **2 处真实泄漏** |
| 7 | 失败原子性 | 多文件补丁中途失败时磁盘状态 | 正确（先全量校验后统一写） |
| 8 | 清理动作与外部护栏 | 脚本的删除是否撞上环境的保护机制 | **1 处**（D-10） |
| 9 | 超时机制是否真的生效 | 设了 timeout 之后进程会不会真的停 | **1 处**（D-11：daemon=False） |

## 二、发现的缺陷与修法

### D-1【严重】判据四处复制且已经漂移

同一套判据在 4 个模块里各有一份，**内容不同**：

| 判据 | 副本 | 实测差异 |
|---|---|---|
| 写意图词 | `preflight` 41 词 / `verify` 22 词 | **互相缺词** |
| 验证命令 | `preflight` / `capability` / `evaluate` | 逐字重复 3 份 |
| 只读措辞 | `preflight` / `capability` | capability 多 4 条 |
| 路径正则 | `preflight` / `verify` / `capability` | 3 份逐字相同 |

**具体后果**：任务「修好这个 bug」——
`preflight._WRITE_INTENT` 含 `修好`/`修复`，判为写任务；
`verify._WRITE_INTENT` 两者都没有，于是"目标要求改动"这件事
在两处得出**相反答案**。

**修法**：新建 `harness/intent.py` 作为单一来源，四模块改为导入。
取并集（47 词），理由是两类误判代价不对称：
判成写任务而其实不是 → 多问一句（可见、可恢复）；
判成不是写任务而其实是 → 放行一个假完成（不可见、后果严重）。

**防回归**：`TestIntentSingleSource` 用静态检查禁止任何模块重新定义这些表，
并用 13 个正反用例断言三个模块对同一任务给出一致结论。

### D-2【严重】`evaluate.WRITE_TOOLS` 漏了 `shell`

原值 `("apply_patch",)`，而 `verify` / `certificate` 都是两项。

**后果**：模型常用 `shell` 写文件（`printf 'x' > f.txt`），
于是诊断器认为"这次运行没改动工作区"，把**真正做了改动的运行误诊为
`false_completion`**。

**修法**：补齐为 `("apply_patch", "shell")`，并加测试断言三处一致。

### D-3【严重】恢复深度闸门整套是空壳

书 §5 点名的「死亡螺旋」防线 —— `enter_recovery` / `exit_recovery` /
`depth_exceeded` —— **在生产代码里零调用**。

**后果不是"少了功能"，而是让人以为这道防线存在**。
一个失败的恢复会触发下一次恢复，形成"恢复的恢复"，
症状是失败率上升而 token 消耗爆炸，从日志里看不出因果。

**修法**：接在 `_call_model` 的重试路径上，深度超限时发
`recovery_depth_exceeded` 并停止继续恢复。

### D-4【严重】轨迹 seq 自检恒真

`Trajectory.assert_seqs()` 断言"第 i 条 seq 必须等于 i"。
但 `Trajectory.from_json` 用 `append()` 重建，而 `append` 会写
`msg.seq = len + 1` —— **磁盘上的 seq 被丢弃，断言检查的是自己刚写进去的值**。

**这条比"没有调用点"更隐蔽**：读代码时它看起来完全正确
（有 append、有断言、有 seq 字段）。我第一版修复只是给它加了个调用点，
测试立刻失败才暴露出真正的问题 —— **断言本身是恒真的**。

**修法**：`from_json` 直接构造 `_msgs` 绕过 `append`，让 seq 保留磁盘值；
调用点放在 `Session.read_trajectory()`（读回时 seq 来自字节，是唯一可能损坏的地方）。

### D-5【中】`shell.kill()` 两处资源泄漏

1. 只 `proc.kill()`，**不 `wait()`** → Windows 上留僵尸进程
2. `stdin` / `stdout` / `stderr` 三个管道句柄**从未关闭** → 每次重建泄漏 3 个

**实测**：修前 10 轮 `reset()` 累积 30 个句柄；修后 167 → 172 → **172**，
只在预热阶段增长，之后完全稳定。

### D-6【中】`EventBus` 订阅者异常完全静默

订阅者负责**落盘**与前端推送。裸 `pass` 意味着：它持续失败时事件流会
静默缺条，而运行结果看起来一切正常 —— 正是"看上去正常的失败"。

**修法**：计数 + 保留最近 20 条原因（`subscriber_errors` / `subscriber_error_notes`）。
主流程依然不受影响（这条不变）。

### D-7【低】`safe_on_error_path` 有接口无消费者

书 §5 要求"错误路径上禁用会再次调用模型的副作用逻辑"。
审计核实：整个 harness 只有 `_call_model` 一处调模型，而它本身就是主链路；
压缩摘要器刻意用确定性实现。**即当前不存在这类副作用逻辑**。

**处置**：不删除，把"接口就位但暂无挡点"**写进 docstring**。
删掉会让将来加自动 commit message 时重蹈覆辙；保留而不说明就是空壳。

### D-8【低】`evaluate.py` 脚本直跑时相对导入失败

引入 `intent` 后它变成 `from .intent import`，脚本直跑报
`ImportError: attempted relative import with no known parent package`。

**这是本项目第四次踩同一个坑**。修法统一为一个 `_ensure_package_path()`
（把根塞进 `sys.path` 再绝对导入），并把教训写进该函数 docstring。

### D-9【观察】其余 `except: pass` 31 处均为合理

逐处核过：`queue.Empty`、`BrokenPipeError`、坏 JSON 行跳过、
`ImportError` 降级、响应已发出无法再写 —— 都有正当理由，
且不会掩盖会影响结果的故障。**不做改动**（改了反而是噪音）。

### D-10【工程】基准脚本的清理动作撞上安全删除护栏

（这一条在审计之后、跑基准第 2 层时才暴露，记在这里因为它属于同一轮。）

`bench_layer2.py` 每次跑完用 `shutil.rmtree(ws)` 清理 checkout 出来的仓库。
实测被环境的**安全删除护栏**拦下：NodeBB 仓库有 **4679 个文件**，
超过护栏阈值（50），需要交互确认 → 脚本直接失败退出，**13 分钟的运行为此白跑**。

**处置：不绕过护栏，改本地策略。** 那条护栏是对的 —— 它保护用户数据。

| 改动 | 理由 |
|---|---|
| **复用**已 checkout 的仓库 | 同题再跑不必重新 fetch（省几分钟 × N） |
| 用 `git reset --hard <sha>` + `git clean -fd` 复位工作区 | 这是 git 自己的清理，不碰用户目录、不触发护栏 |
| 删除整个缓存改为显式 `--clean` | 只有用户主动要求时才删，那时他预期就是删 |

**顺带修掉一个真实缺陷**：原实现每次跑都重新 fetch。
benchmark 的常见用法是反复跑同一批题做对比 —— 那是纯粹的浪费。

### D-11【工程】设了超时，但进程不会真的超时

同一轮里紧接着又踩到第二个工程缺陷，症状更具迷惑性。

`bench_layer2.py` 用 `threading.Thread(target=go)` + `th.join(timeout=timeout_s)`
跑 agent。代码读起来超时机制是有效的 —— 但**进程根本不会退出**：

`threading.Thread` 默认**非守护**。主线程 `join(timeout)` 返回后，
Python 仍会等所有非守护线程结束，而那个线程里的 agent
还在继续调模型（SWE-bench Pro 的题可达几百轮）。

实测证据：设了 **900s** 超时，**21 分钟后进程仍然活着**，
线程数 5 → 30 只增不减，日志一个字都没写出。

**这是本轮的第五个"看起来正确、实际不生效"** —— 与前四个（空壳、
恒真断言、资源只在成功路径释放、护栏撞车）同一形态。

**修法两条**：
1. `daemon=True` —— 主线程结束时它不该拖住进程
2. 超时后**明确标记"指标不完整并继续"**，而不是假装它在跑

第 2 条比第 1 条更重要：`daemon` 让进程能退出，但如果只是默默退出，
结果里会出现一条"状态为空、指标全 False"的记录 ——
读的人会以为"agent 什么都没做"，而真相是"它没跑完就被切断了"。
那又是"看上去正常的失败"。

## 三、确认无问题的部分

| 项 | 结论 |
|---|---|
| `LoopConfig` 16 个字段 | 全部被读取，无"配了不生效" |
| 补丁原子性 | 先全量校验、后统一落盘；中途失败不留半成品（实测） |
| 文件句柄 | 生产代码 0 处未用 `with` 的裸 `open()` |
| `assert_monotonic` / `assert_prefix_stable` | 均有调用点，且每轮调用前执行 |
| 能力账本 / 证书 / 子代理 / 验收框架 | 定义与文档声明一致，抽查 14 项全部命中 |

## 四、一条值得记住的教训

**"写了自检"与"自检有效"是两件事。**
本轮 9 个缺陷里有 3 个（D-3 / D-4 / D-5）属于同一形态：
代码读起来完全正确，但**从不生效或从不失败**。

它们的共同特征是：
- 空壳（有定义、无调用点）
- 恒真断言（检查自己刚写进去的值）
- 分支不可达（资源只在成功路径释放）

**检测这类问题的唯一办法是让它失败一次** ——
对每个"防线"都构造一次该被拦住的输入，看它拦不拦得住。
这也是为什么本轮每个修复都配了一个"故意触发"的测试，
而不是"调用一下不报错"的测试。

这一轮实际印证了它：D-3（空壳）、D-4（恒真断言）、D-10（护栏撞车）、
D-11（超时无效）**全都是在"真的去用它"的过程中才暴露的** ——
静态阅读代码时它们看起来都没问题。

### 另一个副产物：本轮共发现 **5 个** 同形态缺陷

D-3 恢复闸门空壳 / D-4 轨迹自检恒真 / D-9 分支不可达（资源只在成功路径释放）/
D-10 清理撞护栏 / D-11 超时无效。

它们分布在不同模块、由不同人（同一轮里由我）写出，但**失效方式完全一致**：
**有代码、有意图、但没有一条能真正拦住东西的路径。**

这条规律值得记进项目纪律：**写完一道防线之后，必须构造一次它该拦的输入。**
