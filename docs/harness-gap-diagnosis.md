## 零、三个必须先认清的事实

调研之后我逐层读了代码，有三个发现比报告里的判断**更严重**：

### 事实 1：`compact()` 从来没有被调用过

```
$ grep -rn "\.compact(" harness/ --include="*.py"
（无结果）
```

`context.py:180` 实现了 `compact()`，注释写得很完整（append-only、不破坏前缀、
为什么不滑动窗口），但**主循环里没有任何调用点**。

**含义**：长会话根本不会压缩。一旦超过模型窗口，行为是**未定义**的
（取决于端点如何处理超长 messages，最常见是 400 或静默截断）。
我们连"压缩悬崖"都还没走到——我们还没有开始压缩。

### 事实 2：`GoalVerifier.record()` 从来没有被调用过

```
$ grep -rn "goal.record" harness/ --include="*.py"
（无结果）
```

`verify.py:257` 定义了 `record()`，`report()` 会统计 `self._results`。
但 `_results` **永远是空列表**，所以：

- `report()["satisfied"]` 永远 = 0
- `report()["all_met"]` 永远 = False（因为 `bool(self.conditions) and 0 >= len(...)`）
- `loop.py:276` 那个分支 `if self.goal.conditions and not self.goal.report()["all_met"]`
  **只要传了 `goal_conditions` 就必然进入**，报"目标未满足"

**含义**：目标验证不是"弱"，是**完全空的**。传 `goal_conditions` 只会让每次运行
都以"目标未满足"结束——一个只会误报的检查器，比没有更糟。

### 事实 3：`verify.py` 的检查跑在与 agent 相同的可写工作区

`Verifier(workspace)` 与 agent 共享同一目录。这意味着 agent 理论上可以：

- 改写 `quick_lint` 依赖的文件
- 创建/修改测试文件让检查通过

这正是 Berkeley BenchJack 在 SWE-bench 上用的手法（丢一个 `conftest.py` 改写测试结果）。
我们没到那个严重程度（我们的检查是结构化的、不看 pytest 输出），
但**"评估器与 agent 共享可写空间"这个结构本身是错的**。

## 二、按缺口严重度排序

### G-1【最高】完成判定没有证据约束 → "假完成"

**代码事实**
- `loop.py:212` `if not reply.tool_calls:` → 直接 `_finish("completed", "任务完成。")`
- 唯一的防线是 `_looks_like_intent_only()`，但它只是**正则匹配意图词**，且上限 2 次

**前沿做法**（arXiv 2608.23623，ECT）
每一条最终声明必须绑定到**有效、在范围内的轨迹证据**，且确定性重放能重建该值。
实验：不安全完成 **0/288 vs 252/288**；过早无支持终止 **0/66 vs 40/66**。

**差距**
我们没有"声明 ↔ 证据"的绑定。`_finish` 的 reason 是**模型自己写的一句话**
（`"任务完成。"`），没有任何东西验证这句话。

**可落地的最小改造**
引入 `CompletionCertificate`：
- agent 要结束时，必须为「它声称已完成的事项」逐条附**证据引用**（seq 号 + 工具 + 产物）
- 一个**确定性**校验器检查：该 seq 是否真的存在、是否是成功结果、是否在范围内
- 任一检查失败 → 返回 `continue` + **原因码**（让模型能针对性修正）

---

### G-2【最高】上下文压缩是空壳

**代码事实**
`compact()` 无调用点。`loop.py` 里只有 `max_tokens_budget`（600k）在**累计用量超限时直接终止**，
**没有任何压缩逻辑**。

**前沿做法**（arXiv 2608.22752，Compaction Cliff）
不加区分的摘要会在 5 轮后把安全规则保留率打到 **10%**。
解法是按类型路由保留策略：硬约束 verbatim、事实结构化、日志可摘要、推理可丢。

**差距**
两层差距：(a) 根本没压缩；(b) 即便接上 `compact()`，它也**不区分类型**
——`middle` 全部丢给一个 `summarizer`，正是压缩悬崖的那条路。

**可落地的最小改造**
1. 在循环里接上压缩触发（按 token 用量比例，而不是等爆）
2. 压缩前先给每条消息**分类**：`constraint` / `fact` / `episode` / `reasoning`
3. `constraint` 永不进摘要器 → 原样保留（并复制到摘要头部）
4. 摘要条目必须标**来源**：有环境输出支持的才写成事实，模型推断写成"（推断，未验证）"

---

### G-3【高】目标验证是空壳且会误报

**代码事实**
`GoalVerifier._results` 永远为空 → `all_met` 恒为 False → 传了 `goal_conditions` 就必然报未满足。

**前沿做法**（ECT + VMAO）
- ECT：证书 + 确定性校验
- VMAO：完整性评分 0-1 + 缺失方面 + **收益递减停止**（每轮改进 <5% 就停）

**差距**
我们连"记录一条证据"都没接上。

**可落地的最小改造**
1. 每条目标条件在**首次被考虑时**注册为 `pending`
2. 每次工具结果进来，用一个**确定性**匹配器把结果挂到候选条件上（不做 LLM 判断）
3. 只有挂了证据的条件才 `satisfied=True`
4. `all_met` 的语义修正为：**所有条件都有证据**（而不是"结果列表长度相等"）

---

### G-4【高】没有 trace → eval 闭环

**代码事实**
`.crucible/runs/<id>/events.jsonl` 有完整事件，但：
- 没有任何代码读它做分析
- 没有回归测试生成
- 没有"这次比上次好还是坏"的度量

**前沿做法**（arXiv 2610.03315 LiteTrajEval + 综述"可观测性—评估缺口"）
**89% 有 tracing，仅 52% 有 evals。** 这是行业最大缺口，我们也在里面。

LiteTrajEval 的做法可整段照搬：
预处理轨迹 → 标记启发式失败信号 → 固定预算序列化 → **单次** rubric 判定 → 结构化诊断报告。
成本是 AgentRx 的 1/6，时间 1/8，定位一致率反而高 20-35pp。

**可落地的最小改造**
新增 `harness/evaluate.py`：
- `analyze_trace(run_dir) -> DiagnosticReport`
- 先做**纯启发式**（不调模型）：假完成、循环、无验证、工具连续失败、超预算
- 可选：单次 LLM 判定补充语义问题（预算受限）

这条**不需要真实模型**就能做，纯规则就能产出可用诊断。

---

### G-5【高】没有能力作用域

**代码事实**
`policy.py` 的判定输入是 `Action`（kind/paths/command）+ 沙箱 + 审批。
**没有"哪个 agent"这个维度**。

**前沿做法**（arXiv 2609.08371 CapScope）
从**可信输入**推导任务级权限上限，给每个 agent 独立类型化能力集，
每次调用对照**发起者**检查。注入执行从 33-47/75 降到 **3/75**。

**差距**
单 agent 场景下暂时等价（因为只有一个主体），但：
1. 没有"任务级权限上限"这个概念 —— 现在权限完全由全局沙箱模式决定
2. 一旦引入子代理，权限会自动传导（这是 CapScope 的核心攻击面）
3. 没有"agent 请求了一个它从未拥有过的能力"的记录

**可落地的最小改造**
即使暂不做多代理，也可以先加**能力账本**：
- 任务开始时确定 `capability_ceiling`（可写路径集合、允许的命令白名单类别）
- 每次工具调用记录 `requested ∩ ceiling`，空的记录为**越权尝试**
- 越权尝试不需要拒绝（沙箱已在做），但**必须可观察**——这是注入检测的信号源

### G-6【中高】工作区没有状态快照

**代码事实**
无快照机制。agent 改坏文件后，恢复手段是它自己动 `shell`（而 `git checkout` 在
`workspace-write` 下是被允许的）——这既是恢复手段也是**破坏手段**。

**前沿做法**（Crab arXiv 2604.28138 + DeltaBox arXiv 2605.22781）
- **>75% 的轮次不产生与恢复相关的状态** → 不需要每轮全量快照
- Crab：eBPF 分类 + 轮次对齐，恢复正确性 8%→100%，流量降 87%
- DeltaBox：只复制变化，检查点 14ms / 回滚 5ms

**可落地的最小改造（纯 Python）**
不做 OS 级 C/R。做**变更集记录**：
- 每次 `apply_patch` / 写文件成功后，把 `(path, old_content_hash, new_content)`
  存进 run 目录（只在文件确实变了时存）
- `rollback(run_id, to_seq)` 逐个文件还原
- 这已经能覆盖 95% 的实际需求（agent 只会通过工具改文件）

### G-7【中】工具描述与错误信息未达前沿标准

**代码事实**
`tools/*.py` 的描述写了"什么时候用"，但**没有系统地写"什么时候不该用"**——
而工程共识是：负例是**对选择准确率提升最大**的那一句，也是大家最常漏的。

错误信息方面，`_cap_output` / `_format_error` 做得不错（会带上层与可重试性），
但不是统一的"下一步该做什么"形态。

**前沿数据**
- 工具 >30-50 个显著退化（我们 6 个，健康）
- 重叠是错误选择的**最大单一原因**
- 把 30 个常见错误改写为"下一步指令"，无人干预恢复率 ~50% → **>80%**

**可落地的最小改造**
1. 每个工具描述补一句「不要用它来做 X（改用 Y）」
2. 抽一个 `errors.py`：所有工具错误走同一套模板
   `出了什么错 + 期望是什么 + 下一步调什么`

---

### G-8【中】无防篡改可核验记录

**代码事实**
`events.jsonl` 是普通追加文件。有 `seq` 单调保证，但**可以被编辑**而不留痕迹。

**前沿判断**（arXiv 2608.23953）
这是三个成熟 harness **共同的缺失**，且被作者点名为**下一个分化轴**。
对 provenance 敏感领域（审计、合规、法务）这是刚需。

**可落地的最小改造（成本极低、辨识度高）**
- 每条事件存 `prev_hash` + `hash`（SHA-256，覆盖 `prev_hash + 本条规范序列化`）
- 链头单独存到 `chain.head`
- 提供 `verify_chain(run_dir)`：任何人可离线核验未被篡改
- 外部锚点（可选）：把最终 `head` 打印进终端日志 / 提交到 git commit message

**这是我们能比 Codex 多做一步的地方**——调研明确指出没有一个 harness 做了。

---

### G-9【中】无子代理 / 无上下文隔离

**代码事实**
单循环，无委派机制。

**前沿做法**
- 真正的收益来自**上下文隔离**，不是"分成两个 agent"（同对话 61.0% → 隔离 87.8% 测试准确率）
- 共享模型有 **latent entanglement**：ρ=0.64-0.71 的过度认可相关性
- 检查点摘要会**朝上游结论方向压缩**，加重问题

**可落地的最小改造**（等 G-1~G-4 立住之后）
- `subagent(task, capabilities, context_allowlist)`：**只给规格，不给上游推理**
- 验证者读**原始产物**，不读生成者的 summary
- 我们恰好有三个字段可配端点 → **可以让验证者用不同模型**

按"**投入小 / 收益确定 / 不依赖其他改造**"排序：

## 四、必须先纠正的两个"设计断言"

调研里有一句话要贴在这里提醒自己：

> **没有上下文隔离的角色分离，只是换了个标签，不是架构改变。**

以及：

> **看起来对但跳过了检查的答案，比明显坏掉的答案更危险。**

我们的 `verify.py` 现在只检查"结构性字段"（有没有越界、有没有声明副作用），
`GoalVerifier` 是空壳。所以现在的实际状态是：
**"检查器存在，但不检查完成度"** ——这恰好是最危险的那一类：
它给人"有验证"的错觉，实际上不做验证。

## 五、我不能确定的（诚实标注）

1. **Terminal-Bench 2.0 上的具体数字**（52.8→66.5 等）来自 LangChain 博客与二手汇总，
   我没有复现。作为方向依据可信，作为精确目标不可信。
2. **ECT 的完整实现**我只看到摘要与部分正文，其"封闭变换语言"的具体设计不清楚，
   我们只能做**简化版**（绑定 seq + 检查成功状态 + 范围），达不到它"确定性重放派生值"的强度。
3. **CapScope 的"可信输入推导权限上限"**在单 agent 场景下如何定义还说不好——
   我们的"可信输入"是什么？用户 prompt？启动参数？这需要进一步设计。
4. **压缩悬崖的 53%→10%** 是在 Claude Code 的 `/compact` 上测的，
   不同压缩策略的绝对值会不同，但**趋势（类型不区分 → 规则蒸发）**应当普适。
