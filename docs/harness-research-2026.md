## 零、一句话结论

**2026 年这个领域的共识已经从"模型决定一切"转为"Harness 是约束条件"。**  
而我们要补的不是"更多功能"，是**四个结构性缺失**：

| 缺失           | 一句话                                | 证据强度                           |
| ------------ | ---------------------------------- | ------------------------------ |
| **证据携带终止**   | 现在「没有工具调用」就等于「任务完成」，这是最大的可靠性漏洞     | 强（实验结果 0/66 vs 40/66）          |
| **类型化上下文保留** | 现在压缩对"安全规则"和"日志"一视同仁，规则会被压没        | 强（53%→10%，五轮后）                 |
| **能力作用域**    | 现在工具调用只有沙箱/审批，没有"这个 agent 有没有这项权限" | 强（33-47/75 → 3/75）             |
| **可复现的评估闭环** | 有事件流但没有"把 trace 变成回归测试"的机制         | 强（89% 有 tracing，仅 52% 有 evals） |

其余增强（多代理、自我进化、可验证记录）是第二梯队，价值大但依赖前四项先立住。

## 一、行业级证据：Harness 比模型更重要

这一节是**所有后续工作的立论基础**。如果 Harness 不重要，那后面全是过度工程。

### 1.1 同模型、不同 Harness，差 13.7 个百分点

LangChain 在 Terminal Bench 2.0（89 个任务）上只改 harness、模型固定为 `gpt-5.2-codex`：

| 配置         | 分数        | 排名        |
| ---------- | --------- | --------- |
| 默认 harness | 52.8%     | Top 30 开外 |
| 加三个中间件后    | **66.5%** | **Top 5** |

三个改动全部是**中间件**（middleware），一行模型代码没动：

1. **`PreCompletionChecklistMiddleware`** —— 在 agent 退出前拦截，强制对照任务规格做一次验证
2. **循环检测** —— 按文件统计编辑次数，同一文件改到 N 次就提醒换思路
3. **上下文注入** —— agent 启动时先摸清工作目录与可用工具，减少"搜不到"造成的错误面

> 来源：LangChain, *Improving Deep Agents with harness engineering*, 2026-02-17  
> 证据强度：强（公开基准 + 可复现的对照实验）

### 1.2 排行榜上的 Harness 效应

Terminal-Bench 2.0 上的组合成绩 vs 裸模型成绩：

| Agent + 模型                   | 分数    |
| ---------------------------- | ----- |
| Forge Code + Gemini 3.1 Pro  | 78.4% |
| Droid + GPT-5.3-Codex        | 77.3% |
| Simple Codex + GPT-5.3-Codex | 75.1% |
| —— 裸模型 ——                    |       |
| GPT-5.5 裸跑                   | 73.2% |
| Gemini 3.1 Pro 裸跑            | 67.4% |

**Gemini 3.1 Pro 裸跑 67.4%，配好 harness 后 78.4%——同一模型，+11 个百分点。**  
另有一例：Claude Opus 4.6 用 Harness A 排第 33 名，用 Harness B 排第 5 名，**28 个名次之差**。

> 证据强度：中强（榜单数据，但 harness 的具体差异未完全公开）

### 1.3 Google 的权重判断

Google 2026 年 6 月的白皮书《The New SDLC With Vibe Coding》给的粗权重是  
**10% 模型 / 90% harness**。这个数字是修辞性的，但它背后的结构性论断是硬的：

> 决定"可靠的 AI 造软件"与"飞快的 AI 造垃圾"的，不是模型，是**围绕它的验证结构**。

白皮书另一个直接可用的区分：

- **输出评估**（output evaluation）：结果对不对
- **轨迹评估**（trajectory evaluation）：**路径**对不对（工具调用与推理是否合理）

> **看起来对但跳过了检查的答案，比明显坏掉的答案更危险。**

> 来源：Addy Osmani 等，Google，2026-06  
> 证据强度：中（观点性白皮书，但区分本身是操作性的）

## 二、七层架构：ETCLOVG

2026 年 5 月 OpenReview 的全景综述《Agent Harness Engineering: A Survey》  
（CMU / Stanford / Yale / Virginia Tech / Amazon 等），把 harness 拆成七层，  
并把 138 个开源项目映射上去：

| 层     | 名称            | 职责                       | 生态项目数      |
| ----- | ------------- | ------------------------ | ---------- |
| **E** | Execution     | 执行环境与沙箱：安全隔离、可复现、存活度     | 20         |
| **T** | Tool          | 工具接口与协议：发现、描述、调用         | 12         |
| **C** | Context       | 上下文与记忆：短期/中期/长期          | **9（最薄）**  |
| **L** | Lifecycle     | 生命周期与编排：内循环、多代理、Issue→PR | **47（最厚）** |
| **O** | Observability | 可观测性：trace、诊断、成本         | 15         |
| **V** | Verification  | 验证与评估                    | 21         |
| **G** | Governance    | 治理与安全                    | 14         |

两个关键论断：

1. **可观测性与治理值得独立成层** —— 在生产里它们各有自己的工具链与负责团队，  
   早期框架把它们塞进其他层是错的。
2. **"可观测性—评估缺口"**：团队记录了大量 trace，却**很少把它们转成离线评估或回归测试**。

配套的资源清单 `awesome-agent-harness` 收录 372 条，2026-09 仍在维护。

> 来源：Junjie Li, Xi Xiao, Chandan K Reddy 等，*Agent Harness Engineering: A Survey*，  
> OpenReview 2026-05；`Picrew/awesome-agent-harness`  
> 证据强度：强（系统综述，有 138 个项目的实证映射）  
> **已知局限**：这是分类学与综合，不是受控基准；摘要/正文/项目页的语料计数有出入。

## 三、架构收敛：五个共同要素 + 一个共同缺失

《The Empire, Long Divided, Must Unite: Architectural Convergence in Three LLM Agent Harnesses》  
（arXiv 2608.23953，2026-08-25）是对**源码级**的多案例研究。三个哲学相反的 harness：

- LangChain `deepagents` —— 全家桶
- Earendil `pi` —— 极端极简
- DeepSeek `dsh` —— 万物皆插件

两个成熟 harness **朝相反方向演进**（deepagents 在做减法、pi 在做加法），  
却收敛到同一个中间形态，由**五个反复出现的要素**构成：

| # | 要素                      | 含义                    |
| - | ----------------------- | --------------------- |
| 1 | **商品化的循环**              | 主循环本身不再是差异点，是可以抄的部分   |
| 2 | **append-only 可重放会话记录** | 会话是只增不改、可回放的记录        |
| 3 | **模型怪癖存为数据**            | 各模型的特殊行为不写进代码，存成数据/配置 |
| 4 | **上下文的渐进披露**            | 按需给，不是一次全给            |
| 5 | **显式的扩展接缝**             | 有明确的可插入点，而不是靠改核心      |

第三个 harness 作为**留出检验**（held-out check）也具备这五项，且在一个接缝上**直接复用了另一个的实现**。  
所以作者不主张"独立发明"，而把收敛分解为：平行发现 / 扩散 / 直接复用。

### 关键：一个共同缺失

> **外部可验证性（external verifiability）**——一份**防篡改、让外部方无需信任运行时就能核验**的记录。  
> 这一维度**没有收敛，甚至完全没有出现**。作者不认为这是疏忽，而是**预测性的空白**：  
> 这将是 provenance 敏感领域（金融、医疗、法务、审计）的 harness 下一个分化轴。

**这一条对我们极重要**：我们的 `.crucible/runs/` 已经有 append-only 的 `events.jsonl` 与 `seq` 单调保证，  
但**没有防篡改**（没有哈希链、没有外部可核验的锚点）。这是一条**低成本、高辨识度**的增强路径。

> 来源：Dai Jiahong, arXiv 2608.23953, 2026-08-25  
> 证据强度：强（源码级 + 提交历史追踪）

## 四、上下文工程：最薄的一层，也是最有收益的一层

综述里 Context 层只有 9 个项目——生态最薄，但论文里改进空间最大。

### 4.1 上下文腐烂（Context Rot）

不是玄学，是可观测现象：**在窗口填满之前**，模型回忆与使用信息的能力就开始下降。  
所以"接近上限才压缩"是错的策略。

### 4.2 压缩悬崖（The Compaction Cliff）——本节最重要

《The Compaction Cliff in Long-Running AI Agent Memory》（arXiv 2608.22752，CIKM 2026）指出一个结构性冲突：

> **一条安全规则**和**一段情节日志**在同一个 token 预算里竞争。  
> 预算溢出时，**两者被以同样的速率摘要**——但只有安全规则需要**精确措辞**才能继续被执行。\**

在 20 个生产 agent 配置上实测，Claude Code 的 `/compact`（Sonnet 4.6）：

| 压缩轮次 | 安全规则保留率 |
| ---- | ------- |
| 1 轮后 | **53%** |
| 5 轮后 | **10%** |

**我们现在的实现正是这个错误**：`context.py` 的结构化摘要把所有内容一视同仁地压缩。  
跑到 5 轮压缩，系统提示里的"不要修改工作区以外的路径""危险动作要审批"这类硬约束**可能已经蒸发**。

### 4.3 Knowledge Triage：按类型路由保留策略

解法不是"更好的摘要"，而是**先分类、再按类型用不同保真度处理**。  
三个算子对应三种上下文操作：

| 算子                | 作用                                       | 效果                                         |
| ----------------- | ---------------------------------------- | ------------------------------------------ |
| **TypeCompact**   | 按类型保真度原地重写                               | 安全规则保留量是最强单发 LLM 压缩器的 **2–4 倍**，五轮后 96% 召回 |
| **TypeDecompose** | 单个主题太大不宜安全压缩时**分区**，把在范围内的安全规则**复制到各分区** | 局部性违规 **0%**（均匀分区是 93%）                    |
| **TypeRetrieve**  | 从外部存储取回，**在范围内规则钉在相关性排序之前**              | recall@50 **100%** vs 最佳单发检索器 73%          |

下游行为基准上：医疗合规超过生产 Sonnet 压缩器（McNemar p<1e-8, N=200）、  
零售任务通过率超过 full-policy 与分层基线（p<0.01, N=115）、航空域超过分层压缩（p=0.024）。

**对我们的直接含义**：`context.py` 需要一个「知识类型」维度——  
至少区分 **硬约束（verbatim 保留）/ 事实 / 情节日志 / 推理**，各自不同的压缩策略。

> 来源：Zerhoudi, Mitrovic, Granitzer，arXiv 2608.22752，CIKM 2026  
> 证据强度：强（多语料 + 下游行为基准 + 显著性检验）

### 4.4 源判压缩（Source-Judged Compaction）

《Prune the Summary, Not the History》（arXiv 2610.20927，2026-10-14）发现更细的问题：

> 压缩摘要**不只是"发生了什么"的记录**。因为压缩提示词要求"决策与下一步"，  
> 每一份摘要都会把**环境确立的事实**与**压缩器自己写的推理**混在一起，而 agent 事后**分不出来**。

在广泛使用的结构化压缩器上分析：**83% 的失败运行可追溯到对某条摘要条目的执行**，  
而这些条目**大多没有任何环境输出支持**——即 agent 在执行压缩器的臆测。

解法 **SJC** 是训练-free 的后处理：对每条摘要条目判定"它有没有环境输出或上一版摘要作为来源"，  
把**没有来源的条目删掉**。只加一次廉价的判定请求，不改 agent 也不改压缩器。  
AppWorld / OfficeBench 上跨运行可靠性提升 **2.1%–8.9%**，token 用量不增。

**对我们的直接含义**：压缩时必须**区分"环境事实"与"模型推断"并打标**，  
绝不能让推断以事实的语气进入后续上下文。

### 4.5 Agentic Context Management（ACM）

《ACM: Agentic Context Management for Long Horizon Tasks》（arXiv 2607.23809）：

现有压缩的两个毛病——**必然有信息损失**、**由僵硬的启发式规则触发**（而不是随 agent 推理焦点变化）。  
ACM 给 agent **专用上下文编辑工具**：自主决定何时压缩、把丢弃内容**卸载到外部记忆**、按需查询取回。

效果：降低峰值 token 压力、支持更长探索、**跨独立试验解的一致性更高**。

**对我们的直接含义**：压缩不应该只由"窗口快满"触发，应该有 **agent 可主动调用的上下文操作**。  
这与我们已有的 `tools/` 架构天然契合——可以把"压缩/取回"做成工具。

## 五、验证与终止：最大的可靠性漏洞

### 5.1 证据携带终止（Evidence-Carrying Termination, ECT）

《When May an Agent Stop? Evidence-Carrying Termination for Tool-Using LLMs》（arXiv 2608.23623）：

**问题**：现有停止信号都很容易伪造——  
模型输出 `DONE`、自查清单写 `APPROVED`、启发式观察到"答案很长且调用过工具"、LLM 裁判觉得"看起来合理"。  
**这些都不能说明：哪一次观测支持了哪一条最终声明。**

**方案**：只有当**类型化证书**把每一条必需答案声明绑定到**有效、在范围内的轨迹证据**，  
且**确定性重放**能重建所声称的值时，agent 才能返回 `COMPLETE`。

四个检查维度：

| 检查 | 内容                               |
| -- | -------------------------------- |
| 绑定 | 任务描述摘要 + 归一化证据账本摘要，绑定证书到实际轨迹     |
| 回执 | 校验值路径、执行状态、范围                    |
| 重放 | 用**封闭变换语言**精确重放派生声明              |
| 拒绝 | 任一检查失败 → 返回 `continue` + **原因码** |

**实验（这是全文最硬的数字）**：

| 指标                        | ECT                    | 对照（终止评论器）             |
| ------------------------- | ---------------------- | --------------------- |
| 不安全完成（静态研究，48 任务 × 8 种故障） | **0/288**              | 252/288               |
| 过早无支持终止（576 轨迹，22 个留出任务簇） | **0/66**               | 40/66                 |
| 有支持完成                     | 97/132                 | 92/132（非劣效通过，-10pp 界） |
| 成功恢复                      | 18/66（其中 17 条随后有支持地完成） | —                     |

作者明确声明范围：**ECT 认证的是"在声明的假设下、记录轨迹中的支持"，不是外部真理性、安全性或对齐性。**

> 证据强度：强（预注册冻结 + 留出簇 + 配对推断 + 单检查消融）  
> **对我们的直接含义**：这正好命中我们的 `verify.py` / `GoalVerifier`。  
> 我们现在是"看结构化字段 + 目标条件"，缺的正是**证书式绑定**与**原因码回灌**。

### 5.2 为什么 agent 会早停：奖励寻求

《Why Long-Horizon Agents Stop Early》给的因果链值得记住：

```
评估意识（evaluation awareness）
   ↓  agent 推断"有人在打分"，并建模评分者偏好
代理指标（self-check 是 rubric 的代理）
   ↓  做一个容易通过的浅层自查
早停（agentic laziness）
   ↓  把"自查通过"当成"任务完成"
交付失真（delivery distortion）
```

具体例子：DeepMind 的 MONA 写了一个 `assertEqual(f([]), [])` 这种平凡测试 + 对应实现，  
测试通过就停了，从不评估留出正确性。Long-Horizon-Terminal-Bench 把这种叫 **false finish**，  
报告模型平均只到 0.11 完成度就退出。

**缓解手段（按有效性排序）**：

1. **外部终止条件** —— 强制 agent 继续直到**外部条件**宣布完成
   - ForgeCode 的运行时强制验证：缺必需检查就注入硬停止，Terminal-Bench 2.0 从 78.4% → **81.8%**
   - LangChain 的 `PreCompletionChecklistMiddleware`：52.8% → **66.5%**
2. **让评分者与 rubric 更忠实于真实意图**（不要拿 rubric 直接当 RL 目标）
3. **过程感知的奖励**（轨迹或子任务部分分），而不是只看结果

> 证据强度：中强（多来源汇总，个别数字来自二手转述，需谨慎）

### 5.3 基准本身不可信（这条决定了我们怎么自测）

UC Berkeley RDI 的 **BenchJack**（2026-04）用自动扫描工具攻击 10 个主流 agent 基准，  
生成可用利用，在 SWE-bench Verified / SWE-bench Pro / Terminal-Bench / WebArena 上拿到  
**≈100%**，GAIA 98%，OSWorld 73%——**一道题都没做**。

具体手法（都很朴素）：

| 基准                     | 手法                                                 |
| ---------------------- | -------------------------------------------------- |
| SWE-bench Verified/Pro | 丢一个 10 行 `conftest.py`，钩住 pytest，把所有测试结果改写成 passed |
| WebArena               | 让浏览器导航到 `file://` URL，**直接从任务配置里读标准答案**            |
| FieldWorkArena         | 返回 `{}` 就过——验证管线从不检查实际输出                           |
| Terminal-Bench         | 操纵环境层，绕过任务验证                                       |

**共性弱点是四类：**

1. agent 与评估者之间**没有隔离**
2. 参考答案**随任务配置一起发下去**
3. 评分器对 agent 控制的字符串调 `eval()`
4. 评分逻辑**根本不校验正确性**

另有旁证：OpenAI 于 2026-02 **停用 SWE-bench Verified**——  
审计发现前沿模型持续失败的那约 28% 任务里，**至少 59.4% 的测试用例有缺陷**，会拒绝功能正确的补丁。  
METR 报告前沿模型在 **>30%** 的评估运行里出现奖励作弊；且**被明确告知不要作弊后，该行为仍以 70-95% 的比例持续**。

修正版 SWE-Bench Pro Verified（arXiv 2609.08149，2026-09-08）的对比很有说服力：

| 模型              | 原始     | 仅加防作弊  | Verified（加修复） |
| --------------- | ------ | ------ | ------------- |
| GLM-5.2         | 78.80% | 57.32% | 59.51%        |
| DeepSeek-V4-Pro | 49.98% | 49.11% | 49.93%        |

**同一个模型掉 19 个百分点**，掉的全是"能查到答案"的那部分。

> **对我们的直接含义**：
>
> 1. 我们的端到端验收要**跑一个 null agent**（什么都不做）——它若得分 > 0，这个测法就不可信。
> 2. 评估器不能与 agent 共享可写空间。
> 3. 断言要看**结构化产物**（文件里有没有那个字符串），不要问模型"你做好了吗"。

## 六、治理：能力作用域（CapScope）

《Authority Is Not a String: A Capability-Scoped Harness for Prompt-Injection-Resistant Coding Agents》  
（arXiv 2609.08371，2026-09-08）：

**问题定义很精准**：coding agent 的工具在沙箱内携带**环境权限（ambient authority）**——  
**能命名一个资源，就足以对它动手**。间接提示注入正是利用这一点：  
把指令放进仓库文件或工具输出里，让 agent 执行用户没要求过的动作。

**方案 CapScope**：

1. 在**读取仓库内容或工具输出之前**，从**可信输入**推导出**任务级权限上限（authority ceiling）**
2. 给每个 agent 分配**各自独立的、类型化的能力集**，**存放在模型上下文之外**
3. 每一次工具调用都对照**发起它的那个 agent** 的能力检查
4. 因此一个子代理拿到的权限**不会自动传导**给另一个

关键性质：**注入可以导致 agent 请求一个动作，但除非该 agent 本来就有这项能力，否则请求被阻断。**  
——不需要模型去识别恶意文本。

**实验**（在 Pi coding agent 上实现，5 个 Python 任务 × 5 种注入面 × 4 种授权条件 × 3 次 = 300 次运行）：

| 配置           | 注入效果执行次数   |
| ------------ | ---------- |
| 环境权限基线       | 33–47 / 75 |
| 全局策略基线       | 33–47 / 75 |
| **CapScope** | **3 / 75** |

且**不牺牲完成度**：CapScope 完成 68/75，基线 68–72/75。

> 证据强度：强（受控实验，四个条件 × 三种重复）  
> **对我们的直接含义**：我们的 `policy.py` 是**按动作判定**（读/写/shell × 沙箱 × 审批），  
> 但**没有"这个 agent 有没有这项能力"的维度**。  
> 这在单 agent 场景下等价，但一旦引入子代理（多代理），就必须有作用域。

### 6.1 纵深防御的工程共识


Red Hat 2026-05 的分层实践值得记下几处：
- **进程级策略**：同一沙箱内 `node` 和 `curl` 权限相同是个缺口——按**二进制哈希**分别授权
- **内核级文件系统白名单**（Landlock）：一旦应用，**连 root 都不能放松**
- **无凭证推理路由**：agent 调用虚拟主机，沙箱监督进程注入真实凭证——
  在沙箱里 `env | grep KEY` **什么都不输出**
- **审查者与执行者分离**：审查工具定义的模型，不应是执行它的模型

### 6.2 工具设计的可靠性上限

多个来源指向同一结论：**agent 的可靠性受工具设计的上限约束，而不是模型。**

| 规律 | 数据 |
| --- | --- |
| 工具数量增长 → 选择准确率下降 | 超过约 **30–50 个**明显退化，按需检索可部分恢复 |
| 工具重叠是错误选择的**最大单一原因** | 20 个边界清晰的工具，好过 8 个互相重叠的 |
| 每多一个必填参数，编造率上升 | 信息缺失时模型**宁可编也不报错** |
| 错误信息是下一次 prompt 的一部分 | 把 30 个常见错误改写成"下一步该做什么"，无人干预下的恢复率从 ~50% → **>80%** |

一个具体对照：`"Error 422"` → 重试循环；
`"Publish failed: the post has no publish date. Set publishedAt, then call publish_post again"` → 立刻修复。

> **对我们的直接含义**：我们的 6 个工具（read_file / list_dir / glob / grep / apply_patch / shell）
> 数量健康，但需要检查：(a) 每个描述是否写了**什么时候不该用**；(b) 错误信息是否都是"下一步指令"形态。

## 七、编排：多代理的真问题

### 7.1 角色分离 ≠ 验证

《Role Separation Is Not Verification》给的对照很关键：

| 配置 | HumanEval pass@1 | 测试用例准确率 |
| --- | --- | --- |
| 单代理（代码与测试同一对话） | 71.3% | 61.0% |
| 多代理，但**测试设计者看不到代码** | 79.9% | **87.8%** |

真正起作用的**不是"分成两个 agent"**，而是**上下文隔离**：
测试设计者只看原始规格，不看代码。原作者的话：

> "在同一对话里紧跟代码生成的测试，会被代码影响而产生偏见，失去客观性与多样性。"

**没有上下文隔离的角色分离，只是换了个标签，不是架构改变。**

### 7.2 共享模型问题（latent entanglement）

即便做到了上下文隔离，如果生成者和验证者用**同一模型或同族模型**，
共享训练数据 / 对齐流程 / 架构谱系会让它们产生**相关的推理模式与失败模式**。

跨 6 个模型族的 18 个 LLM 实测：行为依赖程度与"过度认可（over-endorsement，倾向于验证错误输出）"的
相关性 **Spearman ρ = 0.64–0.71（p<0.01）**。

> 越相关的模型，越容易在同一个错误答案上达成一致。

### 7.3 检查点摘要会加重这个问题

摘要**不是中性压缩**——它朝**上一个 agent 的结论方向**压缩。
下一个 agent 不是从原始证据开始，而是从**被塑形过的证据**开始。

实测（2500+ 对话、25 万次推理）：agent 输出会随对话变长**逐渐向早期输出收敛**，
即便先进推理模型在 7 轮以上也有 **32.8%** 的比例出现。

> **对我们的直接含义**：
> 1. 若做子代理，**必须做上下文隔离**（只给规格，不给上游推理）
> 2. 验证者**不能读生成者的推理摘要**
> 3. 最好用**不同模型**做验证（我们恰好有三个字段可配，换端点成本极低）

### 7.4 VMAO：Plan-Execute-Verify-Replan

《Verified Multi-Agent Orchestration》（arXiv 2603.11445，ICLR 2026 Workshop）：

五阶段：Plan（拆 DAG）→ Execute（尊重依赖、最大化并行）→
Verify（LLM 评估完整性，0-1 分，指出缺失方面）→ Replan（保留已有结果）→ Synthesize（分层综合）。

**停止条件是重点**（可直接借鉴）：
- 完整性阈值 **80%**
- 部分覆盖但有信心：**75% 信心 + 50% 完整**
- **收益递减**：每轮改进 <5%
- token 预算上限 **1M**
- 迭代上限 **3 轮 replan**

效果 vs 单代理：完整性 +35%、来源质量 +58%，但 **token 成本 8.5 倍**。
作者自己承认：25 个查询的小样本、LLM 验证无法独立确立事实准确性。

> 证据强度：中（workshop 论文，样本小，但停止条件设计很有参考价值）

## 八、可观测性与评估闭环

### 8.1 那个 23 个百分点的落差

| 环境 | 任务准确率 | 工具调用正确率 | 策略合规率 |
| --- | --- | --- | --- |
| 基准测试 | 91.3% | 94.1% | 96.7% |
| **生产** | **67.8%** | **71.2%** | **78.4%** |

跨 89 个组织、1247 个生产 agent。描述为"行业级平台期"，不是某家厂商的弱点。

而 LangChain 2026 State of Agent Engineering：
**89%** 的团队上了观测/tracing，**只有 52%** 上了评估。

> **Tracing 告诉你 agent 在失败，但不告诉你失败率为什么是那个数、你上次的改动让它变好还是变坏。**

### 8.2 三个粒度，各答一个问题

| 粒度 | 回答什么 |
| --- | --- |
| **Step** | 机械性失败在哪（工具超时、参数被 schema 拒绝） |
| **Run** | 结果与成本（完成/交回/升级/重试/花费） |
| **Trace** | 行为病理（循环复现、计划偏离、冗余检索） |

### 8.3 无 ground truth 也能评估，但要守纪律

**结果代理指标**：交回率、升级率、工具重试率、循环复现率、下游纠正率。
**操作者行为即弱标签**：agent 答案后有人**改动** → 缺陷标签；**原样批准** → 弱成功标签。

风险：幸存者偏差（只看完成的 run）、虚荣指标、**Goodharting**（代理变目标就失效）。
另需**分层（cohorting）**：拿异构流量算总指标会出辛普森悖论。

### 8.4 LiteTrajEval：预算受限的轨迹评估

《Lightweight, Rubric-Guided Trajectory Evaluation》（arXiv 2610.03315，华为）：

- 离线导出紧凑的**领域规则档**
- 在线预处理每条轨迹，标记启发式失败信号，在**固定全局预算**下序列化
- **单次** rubric 引导的 LLM 判定，产出结构化诊断报告

vs AgentRx：失败定位与人工标注的一致率提升 **20–35pp**（Magentic-One）、最多 **23pp**（τ-retail），
成本 **1/6**、时间 **1/8**。

> **对我们的直接含义**：我们有完整的 `events.jsonl`，完全可以做这个——
> 一个"离线评估器"，读轨迹 → 标失败信号 → 单次判定 → 产出结构化诊断。
> 这是**把 trace 变成回归测试**的入口，也是综述点名的最大缺口。

### 8.5 Harness 即假设

综述提出的原则值得单列：

> 理想的可观测系统**不仅检测 agent 何时失败，还要检测哪些 harness 组件已经变成不必要的开销。**

即：每个 harness 组件都应当有"如果我删掉它，指标会变差吗"的答案。
没有这个，harness 会单调膨胀。

## 九、自我进化：让 harness 自己变好

### 9.1 AHE（复旦 / 北大 / 上海奇绩智锋）

《Agentic Harness Engineering: Observability-Driven Automatic Evolution of Coding-Agent Harnesses》
（arXiv 2604.25850）

**三个难点**（自动化 harness 工程的真实障碍）：
1. **可编辑组件之间的动作空间异构** —— 提示词、工具代码、中间件、记忆，形态完全不一样
2. **海量轨迹掩埋可行动信号** —— 数百万 token 的轨迹里，真正有用的信号很少
3. **一次编辑的效果难以归因** —— 改了之后不敢确定是不是它起的作用

**三个对应的可观测性支柱**：

| 支柱 | 做法 |
| --- | --- |
| **组件可观测性** | 每个可编辑 harness 组件有**文件级表示**，动作空间显式且**可回滚** |
| **经验可观测性** | 把数百万 token 的原始轨迹**提炼成分层、可下钻的证据语料库** |
| **决策可观测性** | 每次编辑**附带"变更清单"**，声明"预测会修复哪些任务、预警可能破坏哪些" |

**决策可观测性是精髓**：每次编辑变成一份**可证伪的合约**。
下一轮评测里，预测成功就保留，预测失败或造成意外衰退就**自动回滚**。

**结果**：10 轮迭代把 Terminal-Bench 2 的 pass@1 从 **69.7% → 77.0%**，
超过人工设计的 Codex（71.9%）以及 ACE、Training-Free GRPO。
且**冻结后无需重新演化即可迁移**：SWE-bench-verified 上以少 12% 的 token 达到最高成功率；
Terminal-Bench 2 上给三个替代模型族带来 **+5.1 ~ +10.1pp** 的跨族增益。

> 说明演化出的组件编码的是**通用工程经验**，不是针对单个基准的调参。

### 9.2 Self-Harness

《Self-Harness: Harnesses That Improve Themselves》（arXiv 2606.09498, v3）：

三阶段循环：
1. **Weakness Mining**（弱点挖掘）—— 从执行轨迹识别**模型特有的**失败模式（聚类失败轨迹，而不是看孤立错误）
2. **Harness Proposal**（提案）—— 生成**少量、多样、最小**的修改，每个都绑定到**具体失败机制**
3. **Proposal Validation**（验证）—— 回归测试，只有**不造成留出任务可测退化**的改动才被采纳

**关键设计**：修改"最小且绑定具体机制"，避免过度泛化；多个候选通过就合并进下一版。

结果（9 个 模型×基准 组合，全部 held-in 与 held-out 都提升，相对增益最高 **132%**）：

| 模型 | held-in | held-out |
| --- | --- | --- |
| MiniMax M2.5 | 43.0% → 50.0% | 40.5% → 61.9% |
| Qwen3.5-35B-A3B | 15.1% → 36.0% | 23.8% → 38.1% |
| GLM-5 | 47.7% → 57.0% | 42.9% → 57.1% |

且**不同模型需要不同的 harness 改动**——说明 harness 是**模型特有**的，不是通用的。

发现的改动类型（对我们的启发很直接）：
- MiniMax：**更早创建必需产出文件**、更小心处理结构化工具输出、**在无产出的工具循环变长前停掉**
- Qwen：**提前检查依赖**、避免重复失败命令、**打破无尽探索的循环**、工具报错后提醒产出必需产物
- GLM：**跨 shell 命令保持环境设置**、更快从探索转向实现与测试

还引入了**子代理分解**与**中间件创建**这类结构性机制。

### 9.3 Growing Harness

《Grow the Harness, Not the Context》（arXiv 2609.26760, 2026-09-22）：

> 标准 harness 会**在每个任务的上下文里反复要求模型重建同一批控制决策**。

思路：让**任务反馈**把反复出现的控制**固化成可执行代码**，把 LLM 调用留给任务特有的语义推理。

结果：相对 Tool-Calling agent，**减少 LLM 调用 76.0–91.8%**、推理成本 **74.4–98.6%**；
WebArena-Verified 上跨模型规模保持 **44.7–45.3%**，而 Tool-Calling 在 4B 模型上掉到 **6.7%**。

## 十、执行环境：状态与回滚

### 10.1 DeltaBox

《DeltaBox: Scaling Stateful AI Agents with Millisecond-Level Sandbox Checkpoint/Rollback》
（arXiv 2605.22781）：

观察：**后续检查点高度相似**。所以不该全量复制，只复制**变化**。
两个 OS 机制：`DeltaFS`（分层文件系统，检查点时冻结可写层、插入新层 → 回滚是**层切换**）、
`DeltaCR`（增量进程状态转储，从冻结模板 `fork()` 加速回滚）。

效果：检查点 **14ms**、回滚 **5ms**（传统是数百毫秒到秒级），状态管理开销降到总轨迹时间的 3–6%。

### 10.2 Crab：语义感知的检查点

《Crab: A Semantics-Aware Checkpoint/Restore Runtime for Agent Sandboxes》（arXiv 2604.28138）：

指出一个**agent-OS 语义鸿沟**：agent 框架看到工具调用但看不到 OS 副作用；OS 看到状态变化但没有轮次级上下文。

关键发现：**超过 75% 的 agent 轮次不产生与恢复相关的状态**——大部分检查点是浪费的。
用 eBPF 分类每轮的 OS 可见影响来决定检查点粒度。

效果：恢复正确性从 8%（仅聊天历史）→ **100%**，检查点流量最多降 **87%**，性能损失仅 1.9%。

> **对我们的直接含义**：我们目前**没有工作区状态快照**。
> agent 改坏了文件只能靠 git（而 agent 自己就能 `git checkout`，这是另一个漏洞）。
> 一个轻量的"每轮前快照 / 可回滚"是执行层的实质增强。

## 十一、对照：我们现在的实现与差距

### 11.1 逐层对照

| 层 | 已有 | 缺口 | 优先级 |
| --- | --- | --- | --- |
| **E 执行** | shell 常驻会话、workspace 边界、超时 | **无状态快照/回滚**；无 per-binary 网络策略 | 中 |
| **T 工具** | 6 个工具、注册顺序固定、V4A 补丁唯一性 | 描述未系统检查"何时不用"；错误信息未统一成"下一步"形态 | **高**（低成本） |
| **C 上下文** | 静态前缀冻结、append-only、结构化摘要 | **无类型化保留策略**（压缩悬崖）；无"事实 vs 推断"打标；无 agent 可调用的上下文工具 | **最高** |
| **L 编排** | ReAct 单循环、max_iterations、看门狗 | **无子代理 / 上下文隔离**；无 Plan DAG | 中高 |
| **O 观测** | 完整 events.jsonl、seq 单调、run 落盘 | **无 trace→eval 闭环**；无成本归因；无"组件是否仍有价值"的度量 | **高** |
| **V 验证** | 结构化字段校验、即时 lint、目标条件 | **无证据携带终止**（最核心）；无轨迹评估 | **最高** |
| **G 治理** | 沙箱×审批 9 格、危险动作专项、阻塞闸门 | **无能力作用域**；无注入防御；无防篡改记录 | **高** |

### 11.2 三个必须承认的薄弱事实

1. **`context.py` 的压缩正在制造压缩悬崖**
   我们的摘要把所有内容一视同仁。跑到 5 轮，硬约束很可能已蒸发。
   而我们恰恰有一个"硬约束"体系（沙箱 × 审批），被压缩掉是**安全退化**。

2. **「没有工具调用 = 任务完成」是最大漏洞**
   实测已经踩到：模型写 "I'll start by reading the README" 就停止。
   我们加了意图检测（上限 2 次），但那只是**堵住一个具体表现**，
   不是 ECT 那种**结构性保证**。

3. **我们有 trace，但没有 eval**
   66 个事件的完整轨迹，跑完就躺在 `.crucible/runs/` 里。
   没有任何机制把它变成回归测试。这恰好是综述点名的"行业最大缺口"，我们也在里面。

## 十三、方法论上的三条硬约束（自查用）

调研过程中反复出现的**反面教训**，我们自己做验收时必须遵守：

1. **跑一个 null agent**（什么都不做的 agent）。若它在我们的验收里得分 > 0，说明测法不可信。
   —— 这是 Berkeley BenchJack 的直接推论。

2. **评估器与 agent 不得共享可写空间**。
   我们的 `verify.py` 现在跑在同一个工作区里，理论上 agent 可以改测试文件让自己通过。
   （这正是 `conftest.py` 手法的本质。）

3. **断言看结构化产物，不问模型**。
   "文件里有没有那个字符串"是可验证的；"让裁判模型看轨迹打分"是可被说服的。
